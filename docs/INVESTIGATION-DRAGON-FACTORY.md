# 蟑龙目标分歧与移动工厂开炮前信号调查

2026-10-15；针对 0.8.2 `dc2dd1742f21`。本次 0.8.3 **扩展采集，不改变警报判定或触发时刻**。没有将“已经开炮”改作危的触发源，也没有把等待固定时长包装成“确认会开炮”。

## 结论与证据边界

- 最新本机蟑龙采集确实出现了当前 AI 目标与 Aiming 网络目标分歧；俯冲前可持续数秒，足以跨过整个预警窗口。现有房主和客机分别使用这两个来源，因此存在双人误报路径。**不能据此认定蟑龙同一次攻击同时锁定两人**。本机日志可证明两个目标来源不同；尚无同场队友端文件，不能声称已经逐帧复现双方实际收到的数据或完成修复。
- 移动工厂的闪灯 / 准备位不是开炮承诺。最新较长客机文件中，9 轮完整准备均有 ready，但只有 5 轮观测到开火输入，4 轮没有。其中 3 轮无输入的准备仍产生本机危提示。
- 当前解码的 AI 路径在准备之后继续评估；还没有核实一个可轮询、具有足够飞扑提前量、且能证明随后必定开炮的中间状态。**这不证明整个游戏不存在其他信号**。武器实例之前没采，不能仅凭 AI 记录排除内部计时或待发射状态。
- 0.8.3 采集补上这两层数据，旧规则保留用于对照。生成工具沿用 0.3.1，无新增网络接口或调用。

第三次本体在 52.601 s 产生危，能力时钟 1.064 s，来源是本机 AI 的本人目标；同一时段 Aiming 仍指向队友，到约 54.607 s、Behavior 转入阶段 7 才变为本人。这与报告的第三次双人提示具有明确的代码解释，但队友端是否收到完全相同的旧值仍待双端对应文件验证。

已独立重解当前构建代码：

- `game+0x6BBE8E` 检查 Aiming 网络行 `+0x10`，非零就跳过本轮权威目标刷新；并非“目标 ID 与 processed ID 相同就一定是当前攻击目标”。
- 现有 `replicated_target()` 校验网络 ID、已处理 ID、当前潜兵和位置模式；它没有把该禁更状态解释成“此值可能属于上一招”。因此一个内部自洽的旧目标能通过现有客机校验。
- 蟑龙 Behavior 108 的阶段 6 调用 `0x1DF840`；能力 254 的喷射输入起点是第 90/60 秒。采集中的目标分歧一直覆盖约 1.0–1.2 s 的预警窗口。
- 不能直接把客机缓存 AI 当作替代来源；有效客机文件中它可以是全零。也不能对所有敌人统一拒绝非零 Aiming flags：其他招式未做相应语义验证。

本次没有用“离哪个潜兵更近”、屏幕方向或对旧目标猜测来替代锁定身份，也没有静默关闭客机蟑龙开关。需要核对飞行控制器同步记录是否能提供本次俯冲的目标信息；未知字段先只保存，不赋予玩家身份。

原生路径（均为当前保留模块重新解码的 RVA）：

| 位置 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| `0x1C3A7D–0x1C3AC4` | 设置准备位并启动准备效果 | 此后一定开炮 |
| `0x1C3ACF–0x1C3B1B` | 准备至少 1,000,000 µs，决策再以 500,000 µs 间隔运行 | 开始准备就已经通过后续决策 |
| `0x1C3BB4–0x1C3C27` | 后续继续读取目标、瞄准 / 视线相关函数和条件 | 预警后这些条件不会变化 |
| `0x1C428C–0x1C42C6` | 评分大于零才调用 `0x4BC940` 提交武器输入；失败直接跳过 | 存在额外、提前半秒的不可取消承诺位 |
| `0x4BC9C0–0x4BC9D3` | 成功路径逐槽调用 `0x786BE0`；后者写输入字节 / 网络输入状态 | 此输入还距首发有多少提前量 |
| `0x61742C–0x6174CE` | ProjectileWeapon 在计时和射击条件满足后直接进入 shot 例程 | 所有输入都立即产生炮弹，或所有输入都有固定蓄力 |

离线实体表核对炮台自身有 ProjectileWeapon、WeaponData、WeaponMagazine；未找到其 WeaponCharge 或 WeaponWindUp 记录。因此不能直接套用其他蓄力武器的进度条。还需观测该炮台 ProjectileWeapon 实例的门限计时、状态字节是否在首发之前出现稳定变化。

即使能读取当前视线 / 准星达标，也只能证明**现在**满足条件；若游戏仍允许下一次决策改变，这与“确认会开炮”不同。若新增采集也无法证明有足够提前量的承诺态，应明确保留这个限制，不能用开炮后报警作为本需求的替代验收。

## 0.8.3 定向采集

本次只在 Diagnostics 增加以下读取，普通警报时序不变：

- 移动工厂炮台 ProjectileWeapon 实例：`0x33266D8` 管理器、`+0x50` 实体表、`+0x68` owner、`+0x78` 实例、步长 `0xA8`；记录 `+8` 门限计时、`+0xC` 间隔、若干状态字节及原始实例。计时不标记为开炮承诺。
- 蟑龙 flying 控制器的网络行：`0x3326DE0`、实体表 `+0x20`、owner `+0x38`、网络数组 `+0x48`、步长 `0x1C`。只记录原始整数 / 字节，不宣称其中有已验证的目标 ID。
- 两种对象的完整 Behavior 网络行 `0xA0`：房主标为 last encoded，客机标为 received；与现有 AI / Aiming / 能力 / 输入及实际危决策同时记录。
- 两种定向采集标称 20 Hz；高耗时仍降至 5 Hz。其他招式维持 10 Hz。文件头增加秒精度 UTC 起始时间和进程单调时钟锚点；后者不是跨电脑共用时钟。
- 新增 10 处当前构建指令 pin；只读、局部有界读取，身份 / owner / 销毁位 / 表头 / 行内容 / 管理器更换校验。任何新增通道异常只记 observation_errors，不中断可用通道。

最小补测步骤见包内 [采集说明](../tools/diagnostics/README-采集说明.txt)。蟑龙需要同场双端文件；移动工厂可单人采，包含实际开炮和只闪灯的对照。无需重采其他招式。
